# 立花証券・ｅ支店・ＡＰＩ

J-Quants の有料プランをやめるための、日本株の株価取得先。実データで確認した
ことだけを書く。推測は書かない。

## なぜ替えるのか

J-Quants の無料プランは **2年分・直近12週間は取得不可**。screen も monitor も
3ヶ月前の株価で判断することになり、**エラーは出ずにそれらしく間違う**。

立花は口座があれば無料で、6501 で **6,279件・2001-01-04 〜 2026-08-21** が
返った。25年半で、当日まで来ている。いま払っている J-Quants の5年より長い。

## 確定していること（すべて実機で確認済み）

| 項目 | 値 |
|---|---|
| 専用ＵＲＬ | `https://kabuka.e-shiten.jp/e_api_{版}`（検証は `demo-kabuka`）。**版を固定値で埋めないこと**、下記参照 |
| 公開鍵の登録形式 | **X.509 SubjectPublicKeyInfo の PEM**、BEGIN/END 行を含めてそのまま |
| 鍵の条件 | RSA、2048 または 4096 bit、SHA-256（画面の注記） |
| 仮想ＵＲＬの暗号 | **RSA-OAEP（MGF1-SHA256 / SHA256, label なし）**。平文末尾に改行が付くので落とす |
| 送信方法 | 既定 POST（本文が JSON 文字列、`Content-Type: application/json`）。GET も可で、その場合 `?` の後ろは**生の JSON**（percent-encode しない） |
| 文字コード | **ShiftJIS** |
| 必須の共通項目 | `p_no`（要求ごとの通番）、`p_sd_date`（`.000` 固定）、`sJsonOfmt`（`"5"`） |
| エラー判定 | 2段。伝送層 `p_errno`/`p_err` → 業務層 `sResultCode`/`sResultText` |
| 仮想ＵＲＬの寿命 | 当日限り。`p_no` とともに保存して使い回す |
| 時価配信の口 | `sUrlEventWebSocket` だけ `wss://` で返る |

## 版の寿命 — 固定値で埋めてはいけない

版はパスの Prefix (`e_api_vNrN`) にあり、**旧版は後継の並行リリースから
およそ60日で停止する**。埋め込むと、停止日から「原因不明の通信エラー」として
現れる。日付から解決し、期限が近づいたら自分で警告する作りにしてある。

| 版 | 公開 | 停止 |
|---|---|---|
| v4r9 | 2026-05-16 | **2026-09-27** |
| v4r10 | **2026-08-29** | 未定 |

`"v4r10" > "v4r9"` は文字列比較では**偽**になる。数値で比べること。

### v4r10 で何が変わるか

公式のお知らせ（2026-08-18）によれば、**マスタ等情報の取得方式が、従来の
Ｉ／Ｆから「各個別情報毎問合取得Ｉ／Ｆ」に変わる**。負荷低減が目的とされている。

これは我々に有利に働く。v4r9 の銘柄マスタは `CLMEventDownload` による配信で、
応答を返さず `CLMEventDownloadComplete` まで受け続ける必要があった。v4r10 では
通常の問合せになるため、**株価と同じ作りで書ける**。

並行リリース期間中、v4r9 も動くが追加機能は使えない。v4r10 のマニュアルは
2026-08-29 以降に公開される。**銘柄マスタは v4r10 で実装する。**

## 株価履歴 `CLMMfdsGetMarketPriceHistory`

1要求1銘柄。**日付範囲の指定が無い**ので、毎回全期間（25年分）が返る。

### `xK` 列の正体

これが本実装の要。マニュアルの「始値ｘ分割係数」という説明だけでは決まらない。

**`xK` = raw × （その日より後にある分割係数すべての積）**

つまり **現在の株数単位に直した、分割調整済みの系列**。6501 の実データで、
**25,116個の価格と6,279個の出来高すべてが一致**した（不一致 0 件）。

6501 の分割イベントは2つで、互いに打ち消し合うため見誤りやすい:

| 日付 | 分割前→後 | 係数 | 前日終値 → 当日終値 |
|---|---|---|---|
| 2018-09-26 | 5 → 1（株式併合） | 5 | 777.8 → 3894 |
| 2024-06-27 | 1 → 5（株式分割） | 0.2 | 17620 → 3654 |

- 2018-09-26 より前: 後続の係数の積 = 5 × 0.2 = **1.0** → `xK == raw`
- 2018-09-26 〜 2024-06-26: 積 = **0.2** → `xK == raw / 5`
- 2024-06-27 以降: 後続なし → `xK == raw`

**両端だけを見ると `xK == raw` なので「調整されていない」と読み違える。**
実際に一度そう読み違えた。中間期間（1,401行）を見ないと分からない。

### DB へのマッピング

解析層（`factor_test`、`portfolio/factors`、`portfolio/analysis`、
`seasonality`）はいずれも `adj_close` を読む。したがって:

| DB 列 | 立花の項目 | 理由 |
|---|---|---|
| `open` / `high` / `low` / `close` | `pDOP` / `pDHP` / `pDLP` / `pDPP` | 実際に取引された価格 |
| `adj_close` | `pDPPxK` | 分割調整済み。リターンと factor はこちらを読む |
| `volume` | `pDV` | |

### 差分更新をしてはいけない

`xK` は**最新の分割を基準にした相対値**なので、新しい分割が起きると
**過去の行の値が遡って変わる**。追記型の更新では、分割をまたいだ瞬間に
古い行だけ古い基準のまま残り、系列が不連続になる。

日付範囲を指定できず毎回全期間が返る仕様とも合わせて、**取得のたびに
その銘柄の系列を丸ごと置き換える**のが正しい。

### データの質（6501, 6279件）

- 日付の重複なし、昇順、OHLC の整合崩れなし
- 出来高 0 の日が 1 日ある
- **価格は小数を取りうる**（raw で 1,041行、xK で 2,275行）。整数として
  読んではいけない
- 非分割日には `pSPUO` / `pSPUC` / `pSPUK` の**キー自体が存在しない**（空文字ではない）

## 使い方

`.env` に1行入れると、日本株の株価取得先が全体で切り替わる。

```
JP_PRICE_SOURCE=tachibana
```

単発で切り替えるなら `--source`。銘柄が市場を決め、市場が取得先を決めるので、
米国株が混じっていても自動で yfinance に回る。

```
uv run stock-ai fetch 6501 7203 --source tachibana
```

必要な設定は `TACHIBANA_AUTH_ID`（`.env`）と秘密鍵ファイルだけ。版と接続先は
既定で解決するので、通常は書かなくてよい。

- **銘柄マスタ `CLMIssueMstKabu`**。v4r10 で取得方式が変わるため、v4r9 の
  配信方式は実装しない。v4r10 のマニュアル公開（2026-08-29）を待つ。
- **信用残・証金残・逆日歩**（`CLMMfdsGetShinyouZan` 等、120銘柄/回）。
  J-Quants の無料プランには無いデータ。
- **全銘柄を回したときの所要時間と転送量**。1要求1銘柄で毎回25年分が返る。
  6501 の応答は 1.5 MB だったので、1,564銘柄なら単純計算で 2.3 GB になる。
  `bulk-fetch` を立花に対応させる前に実測が要る。
- **要求の間隔**。マニュアルにも公式サンプルにも上限の記載を見つけていない。
  1銘柄ずつ順に投げる前提で、間隔を空ける仕組みは `bulk.py` にある。
- **v4r10 での株価履歴**。`CLMMfdsGetMarketPriceHistory` は時価情報機能なので、
  今回の変更（マスタ等情報の取得方式）の対象外と思われるが、確認していない。
  2026-08-29 以降にプローブを v4r10 で走らせて確かめる。

## 秘密の扱い

- `tachibana_private.pem` — 仮想ＵＲＬを復号する秘密鍵。`.env` と同じ扱い
- `tachibana_session.json` — 当日の仮想ＵＲＬが**復号済みで**入る。これ自体が
  資格情報で、持っていればその日の口座機能を叩ける
- `TACHIBANA_AUTH_ID` — `.env` に置く

いずれも `.gitignore` 済み。プローブは認証ＩＤも仮想ＵＲＬも指紋しか表示しない。
