解約してから「これが無いと動かない」と分かるのが、いちばん困る形になる。

## 2. まだ埋まっていないもの

### ★銘柄マスタ・セクター・市場区分（代替なし）

`src/stock_ai/data/universe.py` と `src/stock_ai/data/jquants_profile.py` が
**どちらも** `https://api.jquants.com/v2/equities/master` を叩いている。
`JP_PRICE_SOURCE` / `JP_STATEMENT_SOURCE` はここに効かない。**設定で切り替え
られる形になっていない。**

影響するコマンド:

- `stock-ai universe`（銘柄一覧の取得と保存）
- `stock-ai factor-test --universe fresh`（`JQuantsUniverse(...).profiles()`）

`docs/TACHIBANA.md` は「株価と銘柄マスタは立花で埋まる」と書いていたが、
**2026-09-03 まで銘柄マスタ側は実装されていなかった。** 同ファイルの「まだ確認していないこと」に
その理由がある。

> **銘柄マスタ `CLMIssueMstKabu`**。v4r10 で取得方式が変わるため、v4r9 の
> 配信方式は実装しない。v4r10 のマニュアル公開（2026-08-29）を待つ。

**2026-09-03、実測して埋めた。** `JP_UNIVERSE_SOURCE=tachibana` で切り替わる。

### ★上場廃止日は使えなかった

**4,441 件中 4,418 件が空**で、値が入っているのは 23 件だけだった。廃止済み
銘柄がマスタに残っているのではなく、**現存銘柄に廃止予定日が入っているだけ**
である。

**立花では生存バイアスを是正できない。** マスタは現存銘柄のみを返す。

これは「マニュアルに項目があること」と「過去のデータが取れること」が別だった
例である。`checks\立花銘柄マスタ確認.bat` はまさにこれを見つけるために書いた。

**ただし J-Quants でなら直せる（2026-09-03 に判明）。** 下の「★生存バイアスは
解約前なら直せる」を見ること。立花で無理だったことと、どこでも無理なことは
別だった。

詳細は `docs/TACHIBANA.md`「銘柄マスタ」。仮想ＵＲＬは `sUrlMaster` で、
株価履歴の `sUrlPrice` とは別の口である。

**ただし即座には壊れない。** 銘柄マスタは DB に保存済みで（3,607銘柄）、
既存の銘柄を使う分には J-Quants を叩かない。壊れるのは**更新**である
— 新規上場・上場廃止・市場区分の変更が反映されなくなる。

### ★生存バイアスは解約前なら直せる — 期限つきの作業が1つ増えた

実測（`checks\生存バイアス確認.bat`、本番、2026-09-03）。

`equities/master` は `date` を取り、**その日時点の一覧**を返す。日付ごとの
名簿が取れるということは、名簿同士の差が廃止銘柄になる。

| 日付 | 返った件数 |
|---|---|
| 2021-06-01 | **400（断られた）** |
| 2021-10-01 | 3,785 |
| 2022-06-01 | 3,823 |
| 2023-06-01 | 3,881 |
| 2024-06-01 | 3,893 |
| 2025-06-01 | 3,790 |

5年ローリング窓の境界は **2021-06 と 2021-10 の間**にある。

名簿同士の差＝その期間に消えた銘柄:

| 期間 | 消えた |
|---|---|
| 2021-10 → 2022-06 | 49 |
| 2022-06 → 2023-06 | 68 |
| 2023-06 → 2024-06 | 84 |
| 2024-06 → 2025-06 | 106 |

**年 49〜106 件、しかも増えている。** 4年で 307 件。1銘柄あたり数千の
シンボル日を持つので、リバーサルのような銘柄日ベースの検証では無視できない。

そして肝心なのは、**消えた銘柄の株価が 5/5 で取れた**ことである。

```
1352  169本  2021-09-06 〜 2022-05-18
1413  155本  2021-09-06 〜 2022-04-22
1448  136本  2021-09-06 〜 2022-03-28
1737  132本  2021-09-06 〜 2022-03-22
1881  136本  2021-09-06 〜 2022-03-28
```

銘柄コードだけ分かっても価格が無ければ何もできないので、ここが本題だった。

**したがって生存バイアスは恒久的な制約ではなく、期限つきの作業である。**

- 直せるのは **2021-09 以降だけ**。それ以前は、いま実行しても窓の外で返らない。
- 解約日 **2026-09-22 を過ぎると、名簿も廃止銘柄の株価も二度と取れない**。
- 実行するのは `checks\廃止銘柄の取り込み.bat`（`stock-ai delisted-harvest`）。
  取得元を **J-Quants に固定**してある。立花のマスタには廃止銘柄が無いので、
  `JP_PRICE_SOURCE` を見に行くと何も集まらないまま成功したように見える。

保存するのは**日付ごとの名簿**であって和集合ではない。和集合しか持たないと、
2023年に上場した会社を2021年の分位に入れられてしまう。生存バイアスを直した
つもりで先読みを持ち込むことになり、直す前より悪い。

名簿は `data/universe_snapshots/` に1日1ファイルで入る。**これは取り直せない
データなので git にコミットして残す。** DB（株価）は立花から作り直せるが、
名簿は解約後どこからも作り直せない。

### 過去に一度間違えた数え方

最初は「スナップショットと **DB** の差」を廃止数として数えた。**DB は上場一覧
ではない**ので、これは「廃止された」と「そもそも取り込んでいない」を混ぜる。
実際 DB 3,609 に対し 2025-06 の名簿は 3,790 で、差 181 は廃止数ではなく
主に取りこぼしだった。廃止を数えるには**名簿同士**を比べる。

### 全銘柄を立花で回したときの所要時間と転送量 — 実測済み、問題なし

実測（`checks\立花スループット計測.bat`、本番、2026-09-03、5銘柄）。

| | 値 |
|---|---|
| 1銘柄あたり | **1.23 MB / 0.21 秒**（約 6,200 本） |
| 3,607 銘柄への外挿 | **4.4 GB / 13 分** |
| 要求間隔を 0.5 秒空けた場合 | 43 分 |

**解約の障害にならない。** 外挿は線形で、DB書き込み・再試行・レート制限は
見ていないので実際にはこれより悪くなるが、桁が変わるほどではない。

## 3. 解約で失われ、どこにも代替が無いもの

移行先を用意しても戻ってこないデータがある。**「移行できた」と「同じものが
取れる」は違う。**

| 失われるもの | J-Quants の項目 | EDINET にあるか |
|---|---|---|
| **会社の通期予想（時系列）** | `FSales` / `FOP` / `FNP` / `FEPS` | **無い。** 有報は実績のみ |
| **開示時刻** | `DiscTime` | **無い** |
| 決算短信そのもの | `fins/summary` | 無い。EDINET は有報・四半期報告書 |

会社予想が取れなくなると、次が動かなくなる。

- `stock-ai sue-census` / `revision-census`（予想と実績の突き合わせ）
- `stock-ai pead-run --surprise sue`

開示時刻が取れなくなると、次が動かなくなる。

- `stock-ai pead-run`（反応日 R が場中か引け後かを決められない）

**予想EPS だけは立花で部分的に埋まる。** `CLMMfdsGetIssueDetail` の `pEPSF`
（一株利益・予想・通期連結）が取れる。ただし**スナップショットであって時系列
ではない**ので、過去の予想は遡れない。今日から貯め始めることはできる。

**決算ドリフトのテーマは2026-09-03に閉じた**（`docs/PREREG_SUE_JP.md`、
`docs/PREREG_PEAD_JP.md` ともに不合格）ので、この2つが止まっても現在の
検証計画には影響しない。**ただし DB に入っている分より後は増えない。**
将来この線を再開するなら、その時点で別の入手経路が要る。

## 3-2. 何が残っているかを、推測ではなく数える

`checks\解約前の棚卸し.bat`（`stock-ai jquants-inventory`）が、上の表を**いまの
DB に照らして**数える。取得はしない。

判断の分かれ目は1つだけである。**「解約後に作り直せるか」。**

| | 作り直せるか | 急ぐか |
|---|---|---|
| 日足の価格（現存銘柄） | 立花から何度でも | いいえ |
| 財務諸表 | EDINET から何度でも | いいえ |
| **日付ごとの上場名簿** | **どこからも無理** | **はい** |
| **上場廃止銘柄の株価** | **どこからも無理** | **はい** |
| **会社の通期予想・開示時刻** | **どこからも無理** | 決算ドリフトを再開するなら |

**5年ローリング窓は解約より先に効く。** いま取れるのは 2021-09 以降で、その端は
解約日を待たずに毎日後ろへ動く。「解約日まで待てる」ものは1つも無い。

棚卸しは「名簿にあって株価が無い銘柄」を数える。**これがそのまま、生存バイアスの
直っていない残りである。** 取り込みが途中で止まっても、この数字を見れば分かる
（銘柄だけ作られて株価が無い状態と、取り込み済みを取り違えない）。

## 3-3. 429 が銘柄ごとの失敗に化けていた（2026-09-04 に判明・修正）

廃止銘柄399件の取り込みで **84 件を取った直後にレート制限に当たり、残り 315 件が
2分で「失敗」した。そのどれ1つも実際には取りに行っていない。** 閉じた扉に約300回
叩きつけた形になる。

`BulkIngester` には対策が入っていた。`bulk.py` にはこう書いてある。

> 継続すると残りの universe を数秒で同じ拒否に費やすことになり、それが
> 「1件も取れないまま実行が終わる」形である

**その通りのことが起きた。** 原因は経路の違いだった。

- 財務側は provider を直接呼ぶので `RateLimitError` がそのまま上がる
- **価格側は `IngestionService.ingest_prices` を通る。** そこの
  `except StockAIError` が `RateLimitError`（`DataError` の一種）を先に飲み込み、
  銘柄ごとの失敗に変えていた

テストは財務側だけを見ていたので、価格側は素通りしていた。同じ現象を記録した
テストの docstring まであったのに、片方の経路にしか効いていなかった。

修正は `ingest_prices` で `RateLimitError` を先に通すだけ。価格側にも回帰テストを
足した（外すと本番と同じ「全件失敗」が再現する）。

## 3-4. 解約後の生存バイアスは、自前で直す

J-Quants の日付つき名簿は 2026-09 で止まる。それ以降どうするか。

**立花のマスタを月に1枚ずつ保存する。** マスタは現存銘柄しか返さないが、それは
1枚だけ見た場合の話で、**2枚あれば差分が「その月に消えた銘柄」になる。**

| | |
|---|---|
| 置き場所 | `data/tachibana_snapshots/YYYY-MM.csv`（git 追跡） |
| いつ書くか | `4-日次自動化` から毎日呼ぶ。その月の分があれば書かない |
| コマンド | `stock-ai universe-snapshot` |

**ファイル名を月にしてあるので、毎日呼んでよい。**「毎月やる」と覚えておく必要の
ある運用は、いずれ忘れられる。忘れた月は二度と埋まらない。

**J-Quants の名簿と同じフォルダに置かない。** 除外の仕方が違う（J-Quants は
投信・指数を396件除き、立花は上場区分で絞る）ので、境目をまたいで差を取ると
**消えてもいない銘柄が「消えた」ことになる。** 混ぜるなら、意図的に、対応を
確かめてから。

1年後には13枚たまる。コストはほぼゼロである。

## 3-5. 一括ダウンロードという経路がある（2026-09-04 に判明）

3-3 で直したのは「レート制限を銘柄ごとの失敗に化けさせない」ことで、**リクエスト
数そのものは減っていない。** 財務取得は `params = {"code": symbol}` で銘柄ごとに
1回、3,700銘柄なら3,700回である。

J-Quants 自身の資料が、この形を「よくある間違い」として名指ししていた。

> 全銘柄ループで `eq daily --code X` を繰り返す →
> `bulk get --endpoint /equities/bars/daily --date YYYY-MM --download`

**`/fins/summary` は一括対応である。** 解約前に取り切りたい会社予想
（FSales/FOP/FNP/FEPS）と開示時刻（DiscTime）は、ここに乗っている。

| | |
|---|---|
| 一覧 | `GET /v2/bulk/list`（`endpoint` / `date` / `from` / `to`、ページングあり） |
| URL取得 | `GET /v2/bulk/get`（`key` か `endpoint`+`date`。**排他**） |
| 返るもの | `{Key, LastModified, Size}` の一覧、または署名付きURL 1本 |
| 認証 | `x-api-key` — **既存の取得経路と同じ** |
| 形式 | gzip 圧縮の CSV。自動展開はされない |
| プラン | Light 以上（Free は `mkt calendar` を除いて不可） |

**専用の CLI を入れる必要は無い。** 認証が同じなので、いまの Python
クライアントからそのまま叩ける。鍵の写しがディスクに増えることもない。

### 署名付きURLの寿命は5分

一覧を全部取ってからまとめて落とすと、後ろのURLが死ぬ。**1本ずつ「取得して
すぐ落とす」**しかない。取り込みを書くときにここを外すと、途中から 403 が並ぶ。

### プラン別の上限と、遡れる年数

同梱の skill（`.claude/skills/jquants-cli-usage/`、`npx skills add
J-Quants/jquants-cli` で入る）に載っている。

| プラン | 1分あたり | 遡れる年数 |
|---|---|---|
| Free | 5 | 12週〜2年12週（CSV/一括は不可） |
| Light | 60 | 5年 |
| Standard | 120 | 10年 |
| Premium | 500 | 20年 |

**`BulkIngester` の既定 `throttle_seconds=0.5` は 120回／分である。** Standard の
上限ちょうどで余裕が無く、Light なら上限の2倍にあたる。**廃止銘柄の取り込みが
84件で止まったのは、これで説明が付く。** 3-3 で直したのは「429を銘柄ごとの失敗に
化けさせない」ことで、速すぎること自体は直していない。

大幅超過が続くと**約5分アクセスが完全に遮断される**。総時間で見れば、2割遅く
叩くほうが5分止まるより速い。

遡れる年数はプランで決まるので、**一覧が覆っている期間を見ればプランが分かる。**
`jquants-bulk-list` はそれを出す。契約内容を思い出してもらうより、返ってきた
ファイルを数えるほうが速い。

### 個別APIも銘柄ごとである必要は無かった

`fins summary` は `--date` を受ける（その日に開示した全銘柄が返る）。うちは
`params = {"code": symbol}` しか送っていない。一括が使えない場合でも、
日付で回すという道がある。

### 実測（`checks\一括ダウンロードの下見.bat`、本番、2026-09-04）

| エンドポイント | 本数 | 覆っている範囲 | 合計 |
|---|---|---|---|
| `/fins/summary` | 83 | 2021-09 〜 2026-09 | **9 MB** |
| `/equities/bars/daily` | 83 | 2021-09 〜 2026-09 | 119 MB |

ファイル名は2通りある。

```
fins/summary/historical/2021/fins_summary_202109.csv.gz   月（6桁）
fins/summary/live/fins_summary_20260904.csv.gz            日（8桁）
```

**5年ぶん。つまり契約は Light（1分あたり 60回）である。** 覆っている年数が
プランの区切りそのものなので、契約内容を思い出さなくても数字から出る。

> **`BulkIngester` の既定 0.5 秒は 120回／分で、Light の上限のちょうど2倍。**
> 廃止銘柄の取り込みが84件で止まった理由がこれである。

**会社予想と開示時刻は 83本・9MB で全部入る。** 銘柄ごとなら 3,700 リクエスト、
一括なら 166（1本につきURL取得と本体で2回）。`checks\財務を一括で取り切る.bat`。

### `NC` は単体だった。接頭辞なしが連結である（2026-09-04 に確認）

`fins.summary` のフィールドには2つの系列がある。

| 系列 | 例 | 中身 |
|---|---|---|
| 接頭辞なし | `Sales` `OP` `OdP` `NP` `EPS` `TA` `Eq` `BPS` | **連結** |
| `NC` 付き | `NCSales` `NCOP` `NCNP` `NCEPS` `NCEq` `NCBPS` | 単体（NonConsolidated） |

うちのコードは接頭辞なしを読んでいる。**それで正しい。**

CLI 同梱のスキーマは `NC` の側に「連結実績」という見出しを付けていて、
そのまま信じると読み先を全部入れ替えるところだった。**見出しではなく、
数字で確かめた。**

`uv run stock-ai statements-show 7203`（2026-09-04）:

| FY | 手元の売上 | トヨタ公表の連結売上 |
|---|---|---|
| 2022 | 31.4兆 | 31.4兆 |
| 2023 | 37.2兆 | 37.2兆 |
| 2024 | 45.1兆 | 45.1兆 |

単体なら12兆台になる。**桁の大小どころか、値そのものが各年で一致した。**
持株会社を1社見れば足りる、という形の確認である。

| 2024 | 75.00 | 365.94 | 20% |
| 2025 | 90.00 | 359.56 | 25% |
| 2026 | 95.00 | 295.25 | 32% |

2022 だけ突出している。トヨタの FY2022 の配当は分割後で 52円なので、148 は
そちらとも合わない。**同じ行の EPS・BPS・株式数は分割後の尺度で公表値と
一致している**ので、その行の中で配当だけ尺度が違うことになる。

読んでいるのは `DivAnn`（当期実績の年間配当）。分割は 2021-09-30 実施で、
FY2022（2021-04〜2022-03）はそれをまたぐ。**分割前後で尺度の違う値を
組み合わせる**——このプロジェクトが最初に挙げている型そのものである。

一括取り込みはこの行を上書きする（`upsert_reports` は値のある列を書き換える）
ので、**直るか残るかがそこで分かる。** 残ったら、`DivAnn` の分割調整を疑う。

#### `restated()` はこれを直せない（2026-09-05）

まだ原因は確かめていないが、**直し方の側は確かめた。直せない。**

`restated()` が揃えられるのは、1期まるごとが1つの尺度に乗っているときだけで
ある。分割の年の年間配当が「分割前の中間配当 ＋ 分割後の期末配当」だとすると、
**その1つの値の中で尺度が混ざっている。** 148 のままでも、5で割った 29.6 でも
正しくない。しかも `restated()` はその期を最新の尺度とみなすので、**倍率1で
そのまま通す。** 例外は出ない。

そこで直さず、**名指しする**ようにした。`dividends_crossing_a_split()` が
「株式数が整数倍になった期のうち、年間配当を持つもの」を返し、取り込みが銘柄
ごとに1度だけ警告を出す。期末配当しか出さない会社ならまたいでも混ざらないので、
**これは疑いであって断定ではない。** 返すのは確かめる価値のある期である。

警告を `restated()` 側に置かなかったのは、あれが増配率・CAGR・連続増配の
それぞれから呼ばれるためで、同じ行が1銘柄で何度も並ぶ。

### `Eq`（純資産）を「自己資本」の列に入れていた（2026-09-04 に判明・修正）

全83本を入れたあと、トヨタ 7203 で**自己資本の列だけが全年で増えた。**
売上・利益・EPS・BPS・株式数は1円も動いていない。

| 2025 | 359,248 | 368,789 | +9,541 |
| 2026 | 399,189 | 410,201 | +11,012 |

**差の 0.91〜1.10兆は、非支配株主持分そのものである。**

J-Quants のスキーマは2つを別に持っている。

| | |
|---|---|
| `ShEq` | **自己資本**（親会社持分） |
| `Eq` | **純資産**（非支配株主持分を含む） |

`EquityAttributableToOwnersOfParentIFRSSummaryOfBusinessResults`
＝親会社持分を入れる。**同じ列に、定義の違う2つの量が入っていた。**

この列は ROE（自己資本利益率）と PBR の分母に使われる。どちらも慣行として
自己資本を使うので、`ShEq` を先に読むよう直した。`ShEq` が無いときは `Eq` で
代用するが、**代用した件数を警告に出す。** 黙って混ぜるのが、この種の不具合が
高く付く理由である。

**直したあと入れ直して確認した（2026-09-04）。** 5年とも一括前の値に戻った。

| 2022 | 262,460 | 262,460 |
| 2023 | 283,387 | 283,387 |
| 2024 | 342,210 | 342,210 |
| 2025 | 359,248 | 359,248 |

その2つが表示の桁まで一致した。`ShEq` が正しい読み先であることと、EDINET の
IFRS 側の対応が正しいことが、同時に確かめられたことになる。

### 同じ誤りが EDINET 側にもあった（2026-09-05 に確認・修正）

疑いとして書いてあったものを確かめた。**そのとおりだった。**

| 基準 | 要素名 | 中身 |
|---|---|---|
| IFRS | `EquityAttributableToOwnersOfParent…` | 親会社持分＝自己資本 |
| 日本基準 | `NetAssetsSummaryOfBusinessResults` | **純資産** |

つまり同じ `equity` 列が、**会計基準によって別の量を持っていた。** 一律に
間違っているより悪い——IFRS 適用会社と日本基準の会社を並べて比べたとき、差が
会計基準と相関する。

**日本基準の「主要な経営指標等」に、自己資本の絶対額は無い。** 実ファイル
（6501・7203・8306・9020）で確認した。あるのは純資産額・自己資本比率・
自己資本利益率・1株当たり純資産額の4つだけ。だから**自己資本比率×総資産**で
導く。両方とも同じ表の同じ期にある。

#### どちらが正しいかは、同じ表の ROE が決めた

J-Quants と突き合わせるつもりだったが、有報1本の中だけで決着が付いた。
三菱UFJ（8306）の四期前:

| | |
|---|---|
| 純資産額 | 17.99兆 |
| 自己資本比率 × 総資産 | **17.00兆** |
| 差 | **約1兆円**（非支配株主持分） |

親会社株主に帰属する当期純利益 1.131兆を、それぞれで割る。

| 分母 | 出る ROE | 報告された ROE |
|---|---|---|
| 純資産 | 0.0629 | 0.0668 |
| **自己資本** | **0.0665** | 0.0668 |

**残る 0.0003 は期中平均と期末値の違いで説明が付く。** 純資産側の 0.0039 は
説明が付かない。

JR東日本（9020）でも向きは同じで、差は 1.1% と小さい。**小さいから直さない、
にはしない。会社ごとに差が違うということは、直さなければ会社間の比較にその差が
そのまま乗るということである。**

導出できないとき（自己資本比率か総資産が欠けるとき）は純資産で代用するが、
**有報1本につき1行の警告を出す。**

### 直したはずの側が、半分しか直っていなかった（2026-09-05）

上の 2026-09-04 の修正は `normalize_statements`（財務諸表の系列）だけに入って
いて、**`normalize_statement`（スナップショット）は `Eq` を直に読んだままだった。**

同じ `records` から作る2つの出力で、`statements` は自己資本、`snapshot` は
純資産。`screen --max-pbr` はスナップショット側を読む。**例外は出ない。**

部品のテストは両側とも通っていた。無かったのは**同じ入力から出る2つの出力を
突き合わせるテスト**で、これは `factor_panel` と `build_estimators` の符号が
逆になっていた件と同じ形である。

### 先に測る。作らない

`checks\一括ダウンロードの下見.bat`（`stock-ai jquants-bulk-list`）は
**1バイトも落とさない。** 見るのは3つ。

1. **本数** — 月次なのか日次なのかが分かる
2. **覆っている期間** — 一括のほうが短ければ、乗り換えると行が減る
3. **合計サイズ** — 期限内に落とし切れる量か

2 が肝である。**一括に乗り換えて行数が減っても、例外は出ない。**
このプロジェクトで繰り返し起きているのは、まさにその形の不具合である。
粒度を推測して取り込みを書く前に、実物の本数と範囲を見る。

#### b'. Premium まで上げると何が増えるか

**Premium 固有のもの**（Standard に無い）。

| コマンド | 中身 | このプロジェクトでの位置 |
|---|---|---|
| `fins details` | 財務諸表 BS/PL/CF（20年） | **因子の材料。閉じた方向** |
| `fins dividend` | 配当金情報（20年） | 候補5（権利落ち）。**クラスタ数が足りないと自分で書いてある** |
| `mkt breakdown` | 売買内訳データ（20年） | フロー。**機構の族としては近いが、日本での報告が乏しい** |
| `deriv futures` / `deriv options` | 先物・オプション（20年） | **別の資産クラス。** 契約の話ではなく設計の話になる |

**Premium 固有の中身は、記録が閉じた方向に偏っている。** `fins details` と
`fins dividend` は「もっと良い因子」の材料であり、7本の結論は「縛っているのは
因子ではなく設計である」だった。

#### b''. ただし1つ、性質の違う効き方がある — **名簿が20年**

`eq master` は Standard で10年、Premium で20年になる。**これは因子の材料では
なく、生存バイアスを直せる範囲である。**

52週高値で OOS を 2021-10 以降（1,197日）に切ったのは、**廃止銘柄の株価が
そこからしか無かったから**だった。名簿が伸びれば、そこが伸びる。

実測の SD（20日保有、6.47%、膨張2.29倍）をそのまま当てた算術。

| 名簿の範囲 | OOS に使える日数 | 必要な差 | ＋費用 |
|---|---|---|---|
| 5年（いま） | 1,197 | 0.86% | **1.26%** |
| 10年（Standard） | 約2,600 | 0.58% | **0.98%** |
| 20年（Premium） | 約4,800 | 0.43% | **0.83%** |

候補文書が「現実的な水準」と書いた線は **1イベント 1.0%** である。

**これは効果を大きくするのではなく、検出できる差を下げる。** 3つ挙げた
レバーのうち「期間」そのもので、そこは実測で 1.38倍 動いた唯一のレバーだった。

**#3 の話ではない。** #3 は封印前に閉じ、再測定しないと書いてある。これは
**次にイベント型を測るときの算術**である。

#### c. この整理をどう使うか

**ここが動機づけられた推論の入口である。** 候補を3本続けて閉じた直後に
「何が買えるか」を数え上げると、買う理由のほうが見つかりやすい。

**どれも §0 を通していない。** 通るかどうかは測らないと分からず、測るには
データが要る。**「取ってから考える」は、判定の資源を使わない代わりに、
後戻りできない。**

言えることは4つだけである。

1. **名簿の年数は、他で代替できない。** 生存バイアスはこのプロジェクトが
   何日もかけて直してきたもので、10年で倍、20年で4倍になる。**そして
   検出できる差がその平方根ぶん下がる**（上の表）
2. **財務の10年は、ほぼ払う必要がない。** EDINET が同じ範囲を無料・恒久で持つ
3. **`short-sale-report` は候補10本に無かった。** 「制度が需給を作る」という、
   候補1・9 と同じ機構の族で、個別銘柄・イベント型である。**ただし日本での
   報告値は確かめていない**ので、§0 の段2（自分の IS から推定）になる
4. **Premium 固有の中身は、閉じた方向に偏っている。** 財務諸表の全項目も配当
   情報も「もっと良い因子」の材料で、7本の結論はそこではなかった。**Premium を
   選ぶ理由があるとすれば、固有の中身ではなく名簿の20年である**

**買うかどうかを、この一覧の長さで決めない。** 増えるものは数えられるが、
**どれも §0 を通していない。** 通るかは測らないと分からず、測るにはデータが
要る——その循環は、契約を上げても解けない。

### 保存した原本を読み口に通す（2026-09-06）

**「落とせた」と「読めた」は別である。** 原本を 1 GB 保存したあとで読み口が
繋がっていないと分かるのが、いちばん高い。`factor_panel` のときと同じ形で
もある——部品を13個テストしていたのに `build_panel` 自体を一度も呼んで
いなかった。

`jquants_read.census()` が、目録にある原本を1本ずつ開いて（`.gz` なら展開
して）、`key` からエンドポイントを決め、読み口に通して行数を数える。落とす
ことはしないので**解約後にも実行できる。**

- **読み口の無いエンドポイントも件数0で出す。** 消すと、保存できているのに
  一度も読まれていないことが分からなくなる
- **0行は例外を出さない。** 読めたことと中身があることは別なので、別に数える
- エンドポイントは**区切りの数で決めない。** `/derivatives/bars/daily/futures`
  は4つ、`/fins/summary` は2つで、数えると片方が必ず外れる。既知の名前のうち
  いちばん長く前方一致するものを採る

### 契約前にリハーサルをする（2026-09-07）

**Light で取れる7本は、いま保存できる。** 384本・265 MB、待ち時間の下限3分。

やる理由は3つある。**どれも「9/15 の1日を買い戻す」話である。**

1. **課金中の「少数で試す」段を、無料で済ませられる。** 段1 に置いていた
   工程がまるごと前に出る。
2. **保存 → 照合 → 読み口の1本通しを、実物の265 MBで確かめられる。**
   固定データ6本では通っているが、**実物で通したことにはならない。**
3. **9/15 に落とし直さない。** 保存の口は、既にあって大きさの合うファイルを
   落としに行かない。Premium の20年一覧には同じ `key` の2021-2026 が入って
   いるはずなので、**その5年ぶんは飛ばして古い側だけを取る。**

3 が成り立たない（`key` が変わっている）場合でも、大きさが合わなければ
落とし直すだけで、**壊れる側には倒れない。**

**5年ぶんが無駄になるのでは、という懸念は当たらない。** 20年の一覧には5年
ぶんも含まれる。いま取っても 9/15 に取っても、取る本数は変わらない。**変わる
のは、それが課金期間の中か外かだけである。**

### リハーサルで出た2つ（2026-09-07）

**契約前に回した意味がここに出た。** 384本のうち、

| | |
|---|---|
| 保存できた | 139 |
| 落とし直しになった | **171** |
| 429 で落ちた | **74** |
| 照合 | 目録と一致（保存できた310本は壊れていない） |

#### 1. 間隔がプランの上限の2倍だった

既定の 0.5 秒は **120回/分**で、Light の上限は **60回/分**である。

**`recommended_throttle` は前からあったのに、この口が呼んでいなかった。**
`PLAN_REQUESTS_PER_MINUTE` のコメントにも「既定 0.5 秒は Light の上限の2倍」
と**書いてあった。** 書いてあるだけでは防げなかった。

CLAUDE.md にある「CLI側が新しい設定を配線し忘れて、切り替えたはずが常に旧
経路を叩き続けていた」型そのものである。間隔を `JQUANTS_PLAN` から引くように
して、何秒になったかを毎回出す。

#### 2. レート制限を1本ぶんの失敗として飛ばしていた

`RateLimitError` の説明には、**こちらが書いた文章として**こうある。

> 通常の失敗は1銘柄のもので、走行は次へ進むべきである。**レート制限は
> *走行* のものであり、次へ進むことは残りの全銘柄で同じ拒否を集めることに
> 使われるだけである。**

保存の口は、まさにその「次へ進む」をしていた。74本が同じ理由で落ちたのは、
**1回の遅れが74回の失敗に増幅された**結果である。

待って同じ本を取り直すようにした。待ち時間は回を追うごとに伸ばす——同じ間隔
で叩き直すと、向こうから見れば速度が変わっていない。

#### 3. 目録を最後にまとめて書いていた

**171本の落とし直しはこれが原因である。** 途中で止めると目録だけが失われ、
ファイルは残る。次の実行が「あるのに目録に無い」と判断して、**全部を落とし
直す。**

`Ctrl-C` は `except Exception` に掛からないので、失敗の記録では拾えない。
20本ごとに書き、`finally` でも書くようにした。

#### 20年でやっていたら

**1,500本規模で同じことが起きる。** 429 の増幅と落とし直しが重なって、
**丸1日ぶんの契約が消える。** 8日のうち1日である。

**リハーサルの元は取れた。**

**配布サンプル `Stock Prices (OHLC).csv` には有る。一括ファイルには無い。**

**サンプルだけ見て「有る」と思い込むと、静かに外れる。**

###### 直し方 — 調整をこちらで組み立てる

`AdjFactor` は行ごとに入っている（分割の権利落ち日に `0.5` など）。

    adj_close(d) = close(d) × Π{ factor(j) : j が d より後 }

**`j > d` であって `j >= d` ではない。** 権利落ち日の価格は既に新しい基準
なので、その日の係数は掛けない。取り違えると分割日1日だけがずれる。

分割は稀なので、`factor != 1` の行だけ集めれば全期間ぶんでも小さい。取り
込みを2周にした——1周目で分割を集め、2周目で書き込む。

結果: 分割の当たった行 599,472、分割のある銘柄 863。継ぎ目は「普通の1日」
（76銘柄、値動きの中央値 0.8%）に戻った。

###### 診断を1回間違えた

最初は「`AdjC` は、その月より後の分割を知らないのだろう」と書いた。**違った。**

「`AdjC` と違った行 0」という出力を「組み立てが効いていない」と読んだが、
実際は**比べる相手がいなかった**——列そのものが無いので、比較が1回も走って
いなかった。

**「一致した」と「比べていない」が、同じ 0 で出ていた。** `AdjC` が読めた
行数を数えていなかったせいである。いまは両方を並べて出す。

**数えていない値は、0 と区別が付かない。**

継ぎ目の検査は **1日しか見ていない**（2021-09-01）。期間の内側で起きた分割は
そこでは確かめられない。

**組み立てを `j >= d` で書いていたら、継ぎ目は綺麗なまま、分割日だけが1日ずつ
ずれる。** どちらも例外は出ない。

権利落ち日ごとに調整後の収益率を見る検査を足した。正しければ普通の1日に

###### 「大きく動いた」を「間違っている」と読まない（2026-09-07）

権利落ち日の検査を回すと、963件のうち6件が 20% 以上動いた。

```

6731 2026-03-30 -21%、3350 2024-07-30 -25%
```

**これを「組み立てがずれている」と読んだのは早すぎた。** 判定が粗い。

| もし規約を間違えていたら | 実際 |
|---|---|
| **963件全部**が外れる | 6件 |
| 動きは**ちょうど `係数 - 1`**（1:2 なら −50%） | +25%、+38%、−21% |

**どの分割比とも合わない。** 権利落ち日に本当に 25% 動く銘柄はあるし、分割
以外の事由（併合・株式無償割当・合併）でも係数は立ち、その日の動きが係数
どおりにならないことも普通にある。

判定を「大きいかどうか」から「**係数そのものになっているかどうか**」に
変えた。20% 以上でも係数と合わなければ、そう書いて通す。

**閾値で切る検査は、切り方を間違えると本物の異常を見逃すか、正常を異常と
呼ぶ。** ここは後者だった。

**これは4,000銘柄のうち12銘柄である。** ただし 13,780日で「少ない」では
なく **0** なので、系統的な違いがあればどの標本でも出る。

### 項目4 — 行数を数える（2026-09-08）

**銘柄数だけでは、書けたことにならない。** 取り込みは「4,996,413行を書いた」
と言うが、それは `upsert` に渡した数である。**渡したことと入ったことは別で、
入らなくても例外は出ない。**

棚卸しに2つ足した。

| | 意味 |
|---|---|
| 日足の価格 「N 銘柄 / M 行」 | DB 全体（立花の2001年以降を含む） |
| 「原本が覆う … の日足は M 行」 | **取り込みの報告と突き合わせる相手** |

**期間を切らないと比べられない。** DB には立花の2001年以降も入っているので、
全体の行数と取り込みの報告はそもそも一致しない。

窓を渡していないときの 0 を「窓の中に1行も無い」と読ませない——**渡して
いないだけである。**

#### 結果 — 一致した（2026-09-08）

```
原本が覆う 2021-09-01 〜 2026-09-07 の日足は 4,996,413 行。
```

取り込みが「書いた」と言った 4,996,413 と**同じ数である。** 渡した行は
全部入っていた。

数えたのは DB 側で、報告したのは取り込み側である。**別々に数えて同じ数に
なった**ので、片方の数え間違いでは説明が付かない。

### 項目5 — 名簿と株価が、互いに整合するか（2026-09-08）

同じ原本から、2本の経路が出ている。

| 経路 | 元 | 通した絞り込み |
|---|---|---|
| 名簿（`data/universe_daily/`） | `/equities/master` | `normalize_listings` |
| 四本値（DB の日足） | `/equities/bars/daily` | 証券コードの変換だけ |

**2本は同じ絞り込みを通っていない。** 名簿は ETF・REIT・TOKYO PRO Market を
落とすが、四本値は落とさない。だから差が出るのが普通で、**件数を見ても何も
分からない。** 分かるのは理由が言えるかどうかである。

#### 向きを分けて数える

| 見るもの | 意味 |
|---|---|
| 名簿にいて、四本値の行が無い | **警告。** 名簿に載る会社はその日に上場している |
| 名簿にいて、終値が無く出来高も0 | 売買が無かった日。普通にある（実測 161,397 行） |
| 名簿にいて、終値が無いのに出来高がある | **警告。** 「休んだ日」では説明が付かない |
| 終値があって、名簿にいない | 落ちた理由が1件ずつ言えれば、食い違いではない |

**終値の付いた行だけを追う。** 値の付かない行が名簿に無いのは、確かめるまでも
ない。

#### 絞り込みを2つ持たない

落ちた理由は `universe.rejection_reason` が言う。**名簿を作るときに通したのと
同じ関数**である。ここで自前に判定を書くと規則を2つ持つことになり、片方だけ
直したときに気付けない。`normalize_listings` はこの関数を呼ぶように直した。

テストは「理由が付くこと」ではなく **「理由が付くのと、名簿から落ちるのが、
同じ行のときだけであること」** を当てている。

#### 「だいたい説明が付く」で終わらせない

名簿の差 109 件を「たぶん市場が違うのだろう」で済ませかけて、実際には**当時
の市場ではなく最新の市場**を見ていた（2026-09-08）。件数が近いことは説明では
ない。**1件ずつ理由を付けて、理由の言えないものを 0 にする。**

理由が言えない形は2つある。どちらも本当の食い違いだが、**直す場所が違う。**

| 形 | 何が起きている |
|---|---|
| 名簿の原本に行が無い | その日に取引があったのに、名簿に載っていない |
| 原本では残るはずなのに、保存された名簿に無い | **取り出しが落としている** |

口は `checks\名簿と株価が合うか.bat`（`stock-ai jquants-roster-prices`）。
**API を1回も叩かない。**

#### 結果 — 食い違いは1件も残らなかった（2026-09-08）

```
1,227 日 / 名簿 4,595,717 銘柄日
```

| 見たもの | 銘柄日 | |
|---|---:|---|
| 名簿にいて終値もある | 4,550,403 | 99.0% |
| 名簿にいるが売買が無かった | 45,314 | 1.0% |
| **名簿にいるが四本値の行が無い** | **0** | |
| **出来高があるのに終値が無い** | **0** | |
| 終値があるが名簿にいない | 446,010 | |

名簿にいない理由の内訳。

| 理由 | 銘柄日 |
|---|---:|
| 投信・ETF・REIT など | 445,678 |
| 買えない市場（TOKYO PRO） | 332 |
| **理由を言えない** | **0** |

##### 数が閉じた

```
4,550,403 ＋ 446,010 ＝ 4,996,413
```

**一括取り込みが「書いた」と言った数そのものである。** 端数が1行も出ていない。

別々に数えた3つ——取り込みの報告・DB の行数（項目4）・今回の内訳——が同じ数に
なった。**余りが出れば、どこにも分類できない行があるということである。**
出なかった。

##### 「出来高があるのに終値が無い」が 0 だったこと

終値の無い行を「売買が無かった日」と読んでいる。**その読み方そのものの裏付け
である。** 1件でも出来高付きが混じっていれば、読み方か列の意味が違っていた。

##### TOKYO PRO は、上場していてもほぼ売買が成立していない

終値の付いた日が5年で 332 銘柄日、**1日あたり 0.27 日**である。「名簿に出て
株価が1本も無い16銘柄は全部 TOKYO PRO」（2026-09-08）と噛み合う。除いた判断の
裏付けになる。

##### 売買の無かった日が 1.0% ある

名簿にいる銘柄の**約100日に1日**は終値が無い。1日あたり37銘柄。

**これは間違いではないが、収益率を計算するときの穴である。** 前の日の値で
埋めるのか、その日を飛ばすのかで答えが変わり、**どちらでも例外は出ない。**
項目10（20年に伸びて再検討に値する説）で見る。

### 項目6 — 半日立会（`HolDiv=2`）は実在するか（2026-09-08）

コードにはこう書いてある。

> 営業日を `HolDiv=1` かどうかで判定すると、半日立会が非営業日に落ちる。
> 年に数日なので**件数からは気付けない。**

備えとしては正しい。**だが、その区分が手元のデータに1日も無ければ、効いて
いない。** 書いてあることと、在ることは別である。

#### 見る前に書く

固定テストに使っている配布サンプル（`Trading Calendar.csv`、2022年、365日）
には**半日立会が1日も無い。** 一方、テストのもう1つは `2009-12-30,2` を
半日立会として書いている。

そこから立つ予想はこうである。

> **半日立会は古い年にしかない。** 大納会・大発会を終日立会にした年より前に
> 固まっていて、近年には1日も無い。

**この予想が当たるなら、いま持っている 2021-09 以降のデータでは、`1` だけで
絞っても1日も落ちない。** 備えは効いていないことになる。

**外れるなら**——近年にも半日立会があるなら——名簿・株価・カレンダーを使った
「N営業日後」の計算が、すでにずれている可能性がある。

どちらであっても、**20年に伸ばすと話が変わる。** 2006年まで遡れば、半日立会
のあった年が期間に入る。**いまは効いていない備えが、Premium の週に取る20年で
は効き始める。**

#### 数えるもの

| | 何が分かるか |
|---|---|
| 区分ごとの日数（`1`/`2`/`0`/`3` を分けて） | 「営業日 N 日」だけだと、どちらで数えたか後から分からない |
| 半日立会の日付（年ごと） | 大納会・大発会まわりに寄るはず。寄らなければ読み違い |
| `1` だけで絞ると落ちる日数 | **備えの値段そのもの** |
| 一覧に無い区分 | あれば区分が増えている |

#### カレンダーだけを信じない

カレンダーは「立会がある」と**言っている**だけである。本当にその日のデータが
在るかは、別の原本が知っている。名簿（`/equities/master`）と突き合わせる。

| 形 | 何が起きている |
|---|---|
| 立会と言っているのに名簿が無い | どちらかが間違っている |
| 立会でないのに名簿がある | **カレンダーのほうが疑わしい**——名簿はその日の実物である |

**重なる期間だけを見る。** カレンダーは名簿よりずっと長い期間を覆っているので、
全期間で取ると「名簿の無い立会日」が数千日出る。それは欠けではなく、**名簿の
原本がそこまで遡っていないだけ**である。

口は `checks\半日立会は在るか.bat`（`stock-ai jquants-calendar`）。
**API を1回も叩かない。**
